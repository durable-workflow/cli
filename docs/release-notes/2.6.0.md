Durable Workflow CLI 2.6.0

## Resumable batch operations

2.6.0 adds `dw batch:cancel`, `dw batch:signal` and `dw batch:update`, which
act on every workflow a visibility query selects and survive interruption,
plus `dw batch:show` and `dw batch:resume` (cli#60).

```bash
dw batch:cancel --query='customer-42' --reason=offboarded --manifest=cancel-42.jsonl
dw batch:show cancel-42.jsonl
dw batch:resume cancel-42.jsonl
```

- **A manifest before anything is sent.** The selection is written to a new
  private file (mode 0600, never overwritten, never containing your token)
  before the first request. It records the Server, namespace, operation and
  parameters (signal or update input exactly as sent), and every target pinned
  to the run the visibility list reported. Each outcome is appended as it
  happens.
- **One request per target, never resent blindly.** Each target is
  `acknowledged`, `refused`, `skipped` (closed or gone), `pressure` (429, or
  503 with `Retry-After`), `pending` (not yet sent) or `unknown`.
- **`batch:resume`** continues without relisting, so it never picks up a
  different selection or a successor run. It sends only `pending` and
  `pressure` targets, with the same command key, at most three attempts per
  target, and refuses a different Server or namespace.
- **`--deadline`** (for example `--deadline=10m`) bounds a run: unsent
  targets stay `pending` for a later resume.
- **`batch:show`** reads the manifest only; it makes no requests.

### What happens to `unknown` outcomes

A target is `unknown` when its request may have reached the Server but no
definite answer came back: a lost connection, a timeout after sending, a 5xx
response, or a run that stopped between sending and recording. **`dw` never
resends an `unknown` target**, not even on resume, because the original
request may already have taken effect. `batch:show` and `batch:resume` list
these targets; check each one in workflow history and its command receipts,
as described in `docs/batch-operations.md`.

Automatic resolution will need the Server to retain each command key's
admission, so that a repeat with the same key can be answered from the
original outcome. That work is tracked in server#934. Until a Server
advertises it, `unknown` targets stay reported for manual inspection.

## Unchanged

Every 2.x command behaves as in 2.5.1; the new commands are additive. A
parity suite still compares `dw` with the 2.x CLI on every change, offline and
against published PHP Server 2.11.8 and native Servers 3.0.5 and 3.5.0, and a
live batch check runs the new commands against the same Servers. The 2.3.x
PHAR line receives security fixes only until 2027-02-28.
